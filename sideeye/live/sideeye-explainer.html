Draft cheap,
review expensive.

A cheap internal model (Qwen/GLM) writes the code; on demand, a frontier model reads the finished session and reviews it. The trick is token asymmetry: output tokens cost ~5× input tokens — so the cheap model pays the expensive side (writing) and the frontier model pays the cheap side (reading). Near-frontier trust at a fraction of frontier cost.

~80% est. per-session cost reduction vs. frontier-writes-everything — even reviewing every session

Estimate from the pricing model below. Generating a session bills frontier output rates on all code plus repeated context reads; reviewing it is one input-heavy read plus a short critique. No sampling machinery needed at personal/team scale — review 100% and it's still cheap. The internal model's "$0" is no marginal API spend, not free GPUs; the metered gateway is authoritative for judge spend.

How it works

One mode, human-triggered. You're coding with the cheap model and hit a moment of doubt — a design fork, a "tests pass" claim, a finished session you'd like a second pair of eyes on. That moment is the trigger: type a slash command, right in your session. No classifier, no sampling daemon, no gateway changes.

ON-DEMAND review

Ask the expensive model

Two commands for two moments: quick advice on the exchange you're staring at, or a full review of the session's work — a sighted packet sent to a strong judge (Opus 4.8, or Fable 5 for the nasty ones). Review, not re-answer — the judge critiques, the cheap model (or you) revises. Runs in-session, so it always reviews the session you're in.

The money story

The cost game is decided at the baseline — the model that writes every output token of every turn — not at the review. Generation is output-heavy (the ~5× rate); a review is one input-heavy read. That asymmetry is the whole product, and it holds even at a 100% review rate.

What this doesn't prove yet

  • The savings are a model, not a measurement. Real verdicts and metered judge spend replace the estimate. Success = a few weeks of daily use where reviews catch real issues (kept as receipts) and the gateway confirms the cost ratio.
  • The judge reads; it doesn't run. A tier-1 review catches unsupported claims, not unsound ones — an execution-dependent defect with genuinely passing output in the transcript will be missed. Run the tests yourself; agentic (tier-2) verification is future work.
  • "$0" is marginal, not free. The internal model runs on GPUs someone pays for. Any org-scale pitch must cost it at loaded GPU rates, not zero.
  • Sessions can contain secrets. The review packet goes to an external API — fine for self-dogfood; redaction and consent are prerequisites for team-wide rollout.
  • Sampling, taxonomies, and routing are shelved, not rejected. If the MVP proves out and org-scale routable traffic exists, the verdict corpus grown from daily use is the evidence to revisit them — see docs/sideeye-mvp-scope.md.
